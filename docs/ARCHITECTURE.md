# Oratio API — Architecture Guide

This is the guide for the **oratio-api** backend: a single NestJS service for **Oratio**, a Catholic prayer app (daily liturgy, the Rosary, a 33-day Marian consecration, a seasonal "Quaresma de São Miguel" devotion, a prayer library, reading progress, push/notification campaigns, and VoxAI — an AI spiritual-assistant chat).

Read this before touching the code — human or AI agent. It explains what exists, why it's shaped the way it is, and where the non-obvious constraints live. When you make a decision that isn't obvious from the code (a workaround, a security tradeoff, a "why not the simpler way"), record it here or as a comment at the point of use — don't let it live only in a commit message or a chat log.

## 1. Quick facts

| | |
|---|---|
| Framework | NestJS 11, Express platform |
| Language | TypeScript |
| Database | PostgreSQL via Prisma 5 (`prisma/schema.prisma`) |
| Auth | JWT (access + refresh), `passport-jwt` |
| AI provider | OpenAI (`gpt-4.1-mini`), called directly via `axios` — **not** the `openai` SDK |
| Email | Brevo transactional API — raw HTTP via `axios`, not SMTP and not the `@getbrevo/brevo` SDK (see §7/§8) |
| Push | Web Push (VAPID) via the `web-push` package |
| Package name | `finance-api` (historical — see §8, "Naming and dead code") |
| Repo root | `oratio-api/` (sibling to the frontend repo `oratio/`, not a monorepo — no shared package/workspace) |

There is no infrastructure-as-code or deploy manifest in this repo (no Dockerfile, no `render.yaml`/`Procfile`/CI workflow found as of this writing). Hosting/deploy configuration lives outside the repo — check with whoever manages the deployment before assuming a build step.

**Test coverage**: ~96% statements / ~85% branches / ~94% functions / ~97% lines as of this writing (`npm run test:cov`) — every module has real behavioral tests, not just "should be defined" scaffolding. Conventions used throughout, follow them for new specs: `PrismaService` is mocked as a plain object of `jest.fn()`s covering only the methods actually used (never a real DB); external HTTP (OpenAI, the liturgy API, Brevo, `ip-api.com`) is mocked at the module level (`jest.mock('axios')` or `global.fetch = jest.fn()`), never hitting the real network; assertions are state-based (what a function returns, what Prisma was called with), not interaction-only. `collectCoverageFrom` excludes `*.module.ts` and `main.ts` — pure NestJS DI wiring with no branching logic of its own.

**Prisma:** this project has no `prisma/migrations` history. Schema changes are applied directly:

```bash
npx prisma db push       # push schema.prisma to the database
npx prisma generate      # regenerate the Prisma client
```

No npm script wraps these — run them by hand after editing `prisma/schema.prisma`. Because there's no migration history, there's also no rollback path beyond editing the schema back and pushing again; be careful with destructive column/table changes against production data.

## 3. Request lifecycle (`src/main.ts`)

Every request passes through, in order:

1. **`AllExceptionsFilter`** (`src/system-log/`) — catches all exceptions globally, logs 5xx into an in-memory ring buffer (see §7).
2. **`trust proxy`** set to `1` (`app.getHttpAdapter().getInstance().set('trust proxy', 1)`) — the API sits behind Render's reverse proxy, so without this Express's `req.ip` resolves to the proxy's own address instead of the real client. `ThrottlerGuard` keys its rate limits on `req.ip` by default; without `trust proxy`, every user could get bucketed under one shared IP, and the 5/min login limit would end up throttling everyone at once instead of isolating abusive callers. `getClientIp()` (`src/modules/auth/utils/session-info.util.ts`) relies on this too — it reads `req.ip` directly rather than parsing `X-Forwarded-For` by hand, since Express itself now resolves the correct hop.
3. **`helmet`** with `contentSecurityPolicy: false` — this is a pure JSON API; CSP was breaking the verify-email redirect (`GET` request that 302s to the frontend), so it's disabled entirely rather than tuned.
4. **CORS**, restricted to an allowlist (`ALLOWED_ORIGINS` env var, comma-separated; defaults to the production frontend + the Vite dev server if unset — see §9), allowing `Content-Type`, `Authorization`, `X-App` headers, exposing `Authorization`. Not `origin: "*"` — the API is Bearer-token-only (no cookies), so an open CORS policy wasn't a CSRF risk, but it did let any site script requests against public endpoints (register/login/forgot-password) from an arbitrary origin. If you add a client that calls this API from a new origin (a Vercel preview deployment, a new frontend), it needs to be added to `ALLOWED_ORIGINS` or it will be silently rejected by the browser, not the server.
5. **Global `ValidationPipe`** — `whitelist: true, forbidNonWhitelisted: true, transform: true`. Any DTO field not explicitly declared is stripped (`whitelist`) or rejects the request (`forbidNonWhitelisted`). When adding a request field, it must exist on the DTO or it silently disappears (or the whole request 400s, depending on which flag catches it) — there's no partial/loose mode.

The `X-App` header (`AppType.ORATIO = "oratio"`) is checked in several places (see §5). The enum has one member. It's kept — rather than removed — as routing plumbing in case another client is ever added; don't read it as "there are two apps," there is one.

## 4. Domain model (`prisma/schema.prisma`)

One `User` at the center, with these relations. Grouped by feature, not declaration order:

**Auth / session**
- `User` — canonical account row. Email verification, password reset, and email-change all use the same pattern: a random token column + an expiry column on `User` itself (`emailVerificationToken`/`Expires`, `passwordResetToken`/`Expires`, `pendingEmail`/`pendingEmailToken`/`Expires`). No separate token table. Onboarding/consent flags also live here as nullable timestamps — `voxProfile`/`voxOnboardingSeenAt` (§6) and `welcomeSeenAt` (§7) — documented in the sections of their features, not here.
- `RefreshSession` — **one row per device/login**, not a single token field on `User`. This is deliberate: before this model existed, logging in on a second device overwrote the one refresh token on `User`, silently invalidating the first device's session. Now each login creates its own session row; refreshing rotates that same row's `tokenHash`/`expiresAt` instead of creating a new one (see §5).
- `LinkedAccount` — **one row per (social provider, account on that provider)** linked to a `User`. Today only `provider: "google"`; the shape (`provider` + `providerAccountId` + `emailSnapshot` + `linkedAt`, `@@unique([provider, providerAccountId])`) leaves room for Apple later without touching `User`. `providerAccountId` is the provider's stable opaque id (`sub`), **never** the email. `emailSnapshot` records which email the provider asserted (`email_verified: true`) at link time — for auditing a dispute, not for login. Created only after the backend confirms `email_verified: true`. See §5 (login com Google) and `docs/specs/login-google.md`.

**Prayer & devotion features**
- `ConsecrationProgress` / `ConsecrationCompletedDay` / `ConsecrationStage` / `ConsecrationDay` / `Prayer` / `DayPrayer` — the 33-day consecration. `ConsecrationProgress` is one row per user representing the *current* (or most recent) run; `completedAt` distinguishes "finished all 33 days" from "cancelled partway" (cancelling deletes the row; finishing sets `completedAt` and keeps it, because the completion screen and admin stats depend on that distinction). Starting over after finishing deletes the old row (and its completed-day rows) before creating a new one — there is no history of past runs, only the current/latest one.
- `QuaresmaMichaelDay` / `QuaresmaMichaelPenance` — the 40-day "Quaresma de São Miguel" seasonal devotion (Aug 15 → Sep 29, skipping Sundays). Both are scoped by `year` in their unique constraint, because the devotion recurs every year — without `year`, one year's completed days would make the next year's edition read as already-finished on day one.
- `PrayerCategory` / `GeneralPrayer` — the general prayer library (unrelated to the consecration's `Prayer` model — two separate prayer concepts, don't conflate them).
- `RosarySession` — one row per rosary session in progress or completed (`type` = mystery set, e.g. `"gozosos"`; `completed`/`finishedAt` mark completion).
- `SpiritualStats` — one row per user: rosaries prayed, prayers prayed, login/prayer streak. Aggregate counters, updated by the feature services as activity happens (see `ActivityService`). **`prayerStreak`/`lastLoginDate` is a login streak, not a prayer streak** — despite the field name, it's incremented purely by opening the app (`ActivityService.updateLoginStreak()`, from `POST /activity/ping`), unrelated to whether a prayer was actually completed that day. `lastPrayerDate` is the separate field for that (set by `RosaryService.finish()` / `PrayersService`). Code that needs "did the user's streak-preserving action happen today" must use `lastLoginDate`, not `lastPrayerDate` — see §7's notifications bullet for the bug this confusion caused.
- `ReadingProgress` — last reading position for Bible/Catechism ("continue where you left off" on Home). One row per `(userId, kind)`, always overwritten — no history, just a pointer (`reference`/`label`).
- `BibleMark` / `BibleCollection` / `BibleCollectionItem` — the Bible study feature (highlights, favorites, per-verse notes, and named collections). A verse is identified by `book` (the Portuguese name from the frontend's static Bible JSON, same string the frontend routes use) + `chapter` + `verse`. `BibleMark` is **one row per marked verse** with independent `highlighted`/`favorite`/`note` — the service **deletes the row when all three are empty** (there is no "empty mark"), so the row existing is never proof of a specific state on its own. `highlightColor` (`amber`/`green`/`blue`/`pink`/`purple`, validated by `HIGHLIGHT_COLORS` in the DTO) is the marker colour; it is forced to `null` whenever `highlighted` is false, and sending a colour alone turns the highlight on. It is just a colour — there is no per-colour meaning/legend. `reference` ("João 3,16") and `text` (the verse itself) are **snapshots the client sends on every write** — the backend has no Bible text (it lives only in the frontend bundle), and the text is static so the snapshot can't go stale. `BibleCollectionItem` carries the same snapshot fields plus its own optional `note` (separate from `BibleMark.note`). Deleting a collection cascades to its items; collection names are not unique.

**VoxAI (AI chat)**
- `Conversation` / `Message` — a user's chat threads with VoxAI.

**Notifications**
- `PushSubscription` — one row per browser/device Web Push subscription (endpoint + keys).
- `NotificationCampaign` — an admin-triggered broadcast (title/body/url/audience + sent/failed counters). Expires in 15 days; a cron sweeps expired ones.
- `Notification` — one row per user per notification (the in-app "bell" inbox). `source` distinguishes an admin `CAMPAIGN` from an automatic `RULE`. `seenAt` drives the unread badge; `expiresAt` (created + 7 days) removes it from the bell/panel; a cron deletes expired rows.
- `NotificationRule` — the catalog of automatic notification rules (text + on/off + hour + `thresholdDays`/`band` knobs), editable in the admin panel. *When* and *to whom* to fire is code (`condition`, matched by `key`), not data — see `notifications.scheduler.ts`.
- `NotificationSettings` — the anti-spam funnel config as a single lazily-upserted row (`id="default"`); `NotificationRuleVariant` — the per-rule pool of text variants. Both are the 2026-09 "config is data, not constants" overhaul — detailed in §7.
- `UserNotificationProfile` — one row per user caching the per-user time band (`activeBand`) that the notification tick matches rules against — detailed in §7 ("Per-user time band").

**Misc**
- `UserActivity` — a generic activity-feed log (`type`/`action` per row), read by `ActivityModule`.

## 5. Auth module (`src/modules/auth/`)

JWT-based, two-secret design:

- **Access token**: signed with `JWT_SECRET_KEY`, 15 min TTL, validated by `JwtStrategy` (`passport-jwt`, Bearer extraction) on every `@UseGuards(JwtAuthGuard)` route.
- **Refresh token**: signed with a **separate** secret, `JWT_REFRESH_SECRET`, 180-day TTL. Different secret on purpose — a leaked refresh token can't be replayed as a Bearer access token, because its signature won't validate against `JWT_SECRET_KEY`.
- Refresh tokens are hashed with **SHA-256**, not bcrypt, before being stored in `RefreshSession.tokenHash`. Bcrypt truncates input at 72 bytes; since every refresh JWT for the same user shares a fixed prefix (header + `sub` + `email`, before the variable `iat`/`exp`), different tokens for the same user could collide under a truncated bcrypt hash — a rotated-out token could still "validate" against a newer one's hash. A JWT is already high-entropy, so a fast, non-truncating hash (SHA-256) is the correct tool here, and it also enables a direct hash lookup instead of comparing against every session.
- **Rotation, not accumulation**: `refresh()` updates the *same* `RefreshSession` row's `tokenHash`/`expiresAt` rather than deleting and re-creating. The access token's 15-min TTL means the app calls `refresh()` many times a day just to stay logged in — those are the same continuous session, not a new device. Only `generateTokens()` (called from `login()`) creates a new `RefreshSession` row. Confusing these two paths would turn "active sessions" in the profile UI into a list of dozens of rotation artifacts instead of actual devices.
- `AdminGuard` checks `user.isAdmin` from the DB on every request (not cached in the JWT payload) — exported from `AuthModule` and reused by other modules (notifications admin endpoints, etc.), not auth-only.
- Password-reset and resend-verification flows respond identically whether the target email exists or not (`requestPasswordReset`, and the `!user` branch of `resendVerification`) — this avoids leaking which emails have accounts. `resendVerification`'s failure path is the deliberate exception: once execution reaches the "send the email" step, existence is already established by the branches above it, so a real send failure is reported as a real error instead of a fake success.
- **`resetPassword()` revokes every `RefreshSession` for that user**, same as `UsersService.changePassword()` — a password reset is the recovery path used exactly when an account may be compromised, so a leaked refresh token (valid up to 180 days) must stop working the moment the password changes. This wasn't always the case; if you're touching either password-change path, keep both revoking sessions, not just one.
- **Login com Google** (`POST /auth/google`, `AuthService.loginWithGoogle`, spec `docs/specs/login-google.md`). Público, throttle 5/min, `@HttpCode(200)`. O frontend manda o `id_token` (JWT) do Google Identity Services no corpo (`{ credential }`); o backend verifica com `google-auth-library` (`OAuth2Client.verifyIdToken` — assinatura, `aud`, `iss`, `exp`), **reforça o `iss` explicitamente** e **exige `email_verified === true`** (a lib não checa isso, e sem essa checagem a auto-ligação vira tomada de conta). Resolução de conta: `LinkedAccount` por `sub` → senão `User` por e-mail (cria um `User` com `password: null` + `emailVerified: true`, ou **auto-liga** a um `User` existente). Auto-ligar um `User` com `emailVerified: false` **grava `true`** — o Google comprovou a mesma caixa; sem isso a pessoa ficaria barrada pra sempre no `login()` por senha — **e apaga a senha não verificada** (2026-09-14): na mesma `$transaction` do `LinkedAccount`, `password: null`, tokens pendentes (`emailVerificationToken*`, `passwordReset*`, `pendingEmail*`) nulos, **`legalTermsAcceptedAt`/`legalTermsVersion` zerados** (2026-09-14 — o aceite dos Termos/Política dado no cadastro não comprovado foi de quem criou o cadastro, não da dona do e-mail; `LegalTermsGate` pede de novo no primeiro acesso dela) e todas as `RefreshSession` do usuário apagadas antes de `generateTokens`. Motivo: **pré-sequestro de conta** — um atacante cadastra por senha o e-mail da vítima e nunca verifica; manter a senha faria ela logar na conta da vítima depois da ligação. Um `User` já verificado mantém senha e nome. A corrida (`resolveGoogleAfterRace`) passa pelo mesmo `linkGoogleAndIssue`; um `P2002` na própria transação de limpeza desfaz tudo e segue (a requisição vencedora limpou). Cadastro novo roda `user.create` + `linkedAccount.create` num `$transaction`; um `P2002` de corrida (dois cliques) é capturado e o fluxo re-resolve pro vencedor em vez de estourar 500. Emissão de token reusa `generateTokens` — mesma `RefreshSession` que o login normal. A resposta 200 leva, além do par de tokens, **`isNewUser`** (um `User` foi criado agora) e **`googleLinkedNow`** (um `LinkedAccount` foi criado agora para um `User` que já existia) — login recorrente = os dois `false`, nunca os dois `true`; o frontend usa para tela de boas-vindas, toast de auto-ligação e bloqueio de cadastro repetido (spec §"Fase E → E2"). **`nonce` foi deliberadamente cortado** (a versão de fachada não protege de replay — spec, "Fora de escopo").
- **`User.password` é opcional** desde o login com Google. `AuthService.login` numa conta `password == null` responde **`401` com mensagem específica** ("Esta conta entra com o Google…") — reversão da Fase E (§"Fase E → E1" da spec): o app já vaza existência pela mesma rota (a mensagem "verify your email" só aparece pra conta existente), o throttle 5/min limita varredura, e a mensagem genérica só atrapalhava o dono legítimo. O check continua **antes** do `bcrypt.compare`, que quebra com `null`. Quem entrou só por Google define senha por `POST /users/me/set-password` (só aceita quando `password` é `null`, **exige `googleCredential` de um login Google recente** via `assertFreshProof` — §7; **não** revoga sessão, diferente de `changePassword`) ou pelo fluxo `forgot`→`reset` (esse revoga). `GET /users/me` devolve **`hasPassword: boolean`** (`user.password != null`, nunca o hash) **e `hasGoogle: boolean`** (existe um `LinkedAccount` `provider = 'google'` — aditivo pela spec `prova-identidade`, sem schema) — juntos são como o frontend sabe se a conta tem senha, Google, ou **os dois**. `UsersService.changePassword` numa conta sem senha → 409 apontando pra "Definir senha". **`deleteAccount` chama `UsersService.assertFreshProof(userId, { password?, googleCredential? })`** (spec `prova-identidade`): uma prova de identidade fresca além do access token, e **qual** prova vale sai do que a conta REALMENTE tem, não de `password == null`. `proof.password` + a conta tem senha → `bcrypt.compare` (senha errada → 401 `Senha incorreta`); senão `proof.googleCredential` → `AuthService.verifyGoogleIdentity` (mesmo helper do `POST /auth/google`) e o `sub` casando um `LinkedAccount` google **deste** usuário (`sub` de outra conta / sem vínculo → 400, nunca 500; `credential` inválido → o 401 do verificador propaga); nenhuma prova válida → 400. Uma conta com os **dois** métodos prova com qualquer um — assim quem esqueceu a senha ainda consegue exercer o direito de LGPD de apagar a conta. A segurança **não afrouxa**: a exigência de prova continua (uma sessão roubada não apaga a conta), só ampliou quais provas contam. `assertFreshProof` é `private`; consumidores hoje: `deleteAccount` e `setPassword` (2026-09-14). As mensagens de 400 são genéricas ("Não foi possível confirmar sua identidade."). Ampliar para outras operações (trocar e-mail, etc.) é decisão à parte.
- Email verification and email-change confirmation are **idempotent by design**: the token is *not* cleared on success, only checked against the current state (`emailVerified` / `email === pendingEmail`) before acting. Verification links in email are frequently pre-fetched by mail clients (Apple Mail privacy protection, anti-phishing scanners) before the user actually clicks — if the token were cleared on that first "ghost" hit, the user's real click would 401.
- `ThrottlerModule.forRoot([{ ttl: 60_000, limit: 10 }])` is registered inside `AuthModule`, but `@nestjs/throttler`'s `ThrottlerModule` is itself `@Global()` — so once `AuthModule` brings it in, its providers (the default 10 req/min config, storage) are available to the **whole app**, not just `AuthModule`. That's how `UsersController` uses `ThrottlerGuard` on its sensitive routes (`change-password`, `me/email`, `me` delete, admin stats, `setAdminStatus`) without importing `ThrottlerModule` itself. Both controllers apply the guard per-route (not at the controller level, except `AuthController` which applies it class-wide and then tightens specific routes) and override the default with `@Throttle({ default: { limit, ttl } })` where a route needs a stricter cap than the app-wide default (5/min on login, password change, email change, account deletion, and `setAdminStatus` — see the comments at each). VoxAI does **not** use this mechanism at all; it has its own in-memory limiter (§6). If `AuthModule` is ever removed or refactored to stop importing `ThrottlerModule`, `UsersController`'s throttled routes would break at bootstrap (missing DI providers) — this cross-module dependency is easy to miss since `UsersModule` doesn't import `ThrottlerModule` directly. `UsersModule` *does* now import `AuthModule` outright (for the exported `AuthService`, used by `deleteAccount`'s Google re-auth), which happens to make the throttler providers reach it by a second path too — but don't rely on that; the `@Global()` mechanism is the contract.
- **The throttler's storage is in-memory** (`@nestjs/throttler`'s default), same caveat as VoxAI's own rate limiter below: it works correctly today because the API runs as a single instance, but if this service is ever scaled horizontally, every instance counts requests separately and the login/password-reset limits stop being enforced correctly across the fleet. Moving to a shared store (Redis) is the fix, not yet done.

## 6. VoxAI (`src/modules/oratio/voxai/`) — the AI chat feature

The largest and most stateful module (`voxai.service.ts` is ~870 lines). Structure:

```
voxai/
  voxai.controller.ts      routes: chat, chat/stream, bootstrap, conversation CRUD, profile(s)
  voxai.service.ts          conversation state, prompt assembly, OpenAI call, streaming, profiles
  voxai.cron.ts              warms the daily liturgical-calendar cache at 00:01 America/Sao_Paulo
  dto/voxai.dto.ts, dto/set-vox-profile.dto.ts
  guards/vox.rate-limiter.ts    in-memory per-user rate limit (5 req / 60s)
  filters/vox.content-filter.ts  keyword blocklist (horoscope, tarot, occultism, ...)
  prompts/vox.prompt.ts           VOX_IDENTITY (invariant persona/doctrine) + VOX_PROFILES (response styles)
  services/liturgical-calendar.service.ts  fetches/caches the day's liturgical data for the assistant to reference
  utils/brazil-date.ts, date-parser.ts
```

Key points:

- **All routes require `JwtAuthGuard`** (`@UseGuards(JwtAuthGuard)` at the controller level) — VoxAI is never anonymous.
- **Calls OpenAI directly over HTTP** (`axios.post("https://api.openai.com/v1/chat/completions", ...)`), model `gpt-4.1-mini`. There is no `openai` npm package in `package.json` — don't go looking for an SDK client. `chat` and `chat/stream` are separate endpoints/code paths by design ("don't risk what already works" — the streaming path was added later, alongside the non-streaming one, not replacing it).
- **Rate limiting is per-instance, in-memory** (`VoxRateLimiter`, a `Map<userId, timestamp[]>`) — 5 requests/minute per user. This resets on every restart/deploy and does **not** work correctly across multiple server instances (each instance has its own map). If this service is ever scaled horizontally, this needs to move to a shared store (Redis, DB) — it currently silently under-enforces the limit when there's more than one instance.
- **Content filtering is a keyword blocklist** (`contentFilter`), checked before the model is called — not a model-based classifier. It's a first line of defense (occult/esoteric topics), not a complete safety system; the system prompt (`vox.prompt.ts`) is the primary control on what VOX will and won't say, restricting it to Scripture, the Catechism, and Catholic doctrine.
- **Crisis protocol (2026-09-11).** `VOX_IDENTITY` → "Apoio em sofrimento emocional" → `## Crise aguda` is a **precedence rule over every style profile**: on signals of suicidal ideation, self-harm, unbearable suffering or suffering violence, the referral (CVV **188**, chat `cvv.org.br`, SAMU **192**, someone they trust) must not be truncated by the profile's `maxTokens` or by the "be brief" rules — `DIRECT` caps answers at ~4 sentences and would otherwise cut it. It is **doctrine-level, in `VOX_IDENTITY`, not per-profile**: the six profiles change tone, never this. It also forbids offering prayer/a saint as the *sole* way out and framing suffering as punishment or lack of faith, and it explicitly does **not** fire on ordinary questions (including *what the Church teaches about suicide*) so the warning does not become noise. Written against the promise in `oratio/docs/legal/2026-09-11-termos-de-uso.md` §4 — the Terms state the Vox refers people in crisis, so the prompt has to actually do it. Spec: `docs/specs/vox-protocolo-crise.md`.
- **Response profiles (2026-09).** `vox.prompt.ts` is no longer one string: `VOX_IDENTITY` is the invariant persona/doctrine/formatting/liturgy block; `VOX_PROFILES` is a map of 6 style profiles (`DEFAULT` "Padrão", `DIRECT`, `STUDY`, `PASTORAL`, `CATECHIST`, `APOLOGETIC`), each with a `systemAppend` (glued to the *end* of the prompt), a `maxTokens` budget, and user-facing `label`/`short`/`details`/`examples`. The 3 sections that used to force every answer into the same mould ("Aplicação prática", "Arquitetura de uma resposta completa", "Resumo final") were removed from the identity and are now per-profile. **One thing the identity now forces everywhere: every answer opens with an `# H1` title of the topic** — even one-liners (user requirement); what stays conditional is subheadings, the "how to apply" section and the "Em resumo" close. `resolveVoxProfile(key)` falls back to `DEFAULT` for `null`/unknown. `buildSystemPrompt()` is the single assembly point used by both `chat` and `chatStream` (was duplicated). Per-user choice lives in `User.voxProfile` (`null` → behaves as `DEFAULT`); `User.voxOnboardingSeenAt` gates the first-run card. Routes: `GET /oratio/voxai/profiles` (catalog, never leaks `systemAppend`/`maxTokens`), `PATCH /oratio/voxai/profile` (`@IsIn(VOX_PROFILE_KEYS)`, also stamps `voxOnboardingSeenAt`), `POST /oratio/voxai/profile/intro-seen` (dismiss without choosing). `getBootstrap` returns `profile` + `showVoxIntro`. The token log line carries `profile=<key>`. All 6 profiles have their `systemAppend`/`details`/`examples` filled (phase B3); the live 6×5 doctrinal matrix test still needs a human run against the real model (plan `docs/tasks/vox-profiles-plan.md`, phase B3.6).
- **`getOrCreateActiveConversation`** — VoxAI keeps one "active" conversation per user rather than always starting fresh; `POST /conversation` is intentionally the same call as `GET /conversation/active` under the hood ("não cria duplicada" in the source) — calling create twice does not create two conversations.
- `deleteConversation`/`renameConversation` throw NestJS's `NotFoundException` (not a raw `Error`) for a missing or non-owned conversation id — both cases return the same "not found" rather than distinguishing them, so a non-owner can't tell whether an id exists at all. Keep using proper `HttpException` subclasses for expected failure cases in this file; a plain `throw new Error(...)` here becomes an uncaught 500 (the controller has no try/catch) and gets logged into the admin panel's 5xx ring buffer (§7) as if it were a real incident.
- **`utils/date-parser.ts`: "anteontem" must be checked before "ontem"**, not after — `"anteontem"` contains `"ontem"` as a substring, so checking `text.includes("ontem")` first makes it match before the `"anteontem"` branch is ever reached. If you add more relative-date keywords here, check whether one is a substring of another and order the more specific check first.
- `@google/generative-ai` used to sit in `package.json` unused and was **removed in 2026-09-04** (§8). If you find yourself reaching for Gemini, that's a new dependency and a new integration path — an architecture decision, not a detail.

## 7. Other backend modules

- **`src/modules/oratio/liturgia/`** — daily Mass liturgy. `liturgia.service.ts` fetches/assembles the day's readings; `builders/missa.builder.ts` shapes the raw data into the section structure the frontend renders (Ritos Iniciais → ... ), branching on `isDomingo` (Sunday gets a third Eucharistic-prayer option). Public route (`liturgia.controller.ts` has no guard) — liturgy is not user-specific.
- **`src/modules/oratio/home/`** — assembles the Home screen's "For you today" suggestions (`HomeSuggestion[]`): resume an unfinished rosary, continue Bible/Catechism reading, or the day's traditional mystery, each tagged with a short "why" (`"Continue"`, `"Hábito"`, `"Onde parou"`). Read-only aggregation over other modules' data, not its own domain.
- **`src/modules/oratio/consecration/`**, **`prayers/`**, **`reading-progress/`**, **`quaresma/`** — each a straightforward Prisma-backed CRUD/service module per the schema entities in §4. `consecration` and `quaresma` both call into `ActivityService` on completion events (streaks/stats), rather than duplicating that logic.
- **`src/modules/oratio/bible-marks/`** — `PUT /oratio/bible/marks` (upsert one verse's highlight/favorite/note, **merging partial input onto the existing row**, and deleting the row when nothing is left) and `GET /oratio/bible/marks` (all of the user's marks, or `?book=&chapter=` for one chapter). All routes `JwtAuthGuard`. Client always sends the `reference`/`text` snapshot — see §4.
- **`src/modules/oratio/bible-collections/`** — CRUD for `BibleCollection` + add/remove `BibleCollectionItem` under `/oratio/bible/collections`. A missing collection/item **or one owned by another user** both raise `NotFoundException` (never a bare `Error` — same reasoning as `VoxAiService.deleteConversation` in §6), routed through a private `ensureOwned()` check before every mutation.
- **`src/modules/oratio/activity/`** — `ActivityService` centralizes login-streak and activity-log bookkeeping (`UserActivity`, `SpiritualStats`); called by other feature services rather than owning its own user-facing routes primarily.
- **`src/modules/oratio/notifications/`** — three concerns split across files:
  - `notifications.controller.ts` — user-facing: list/mark-seen the bell inbox, push subscribe/unsubscribe.
  - `admin-notifications.controller.ts` — admin-only (`AdminGuard`): create campaigns; manage `NotificationRule`s; edit the anti-spam funnel config (`GET/PATCH .../settings`); CRUD the text variants of a rule (`.../rules/:key/variants`, `.../variants/:id`).
  - `notifications.scheduler.ts` — a `DEFAULT_RULES` catalog (rosary unfinished, streak at risk, Bible/Catechism resume, Sunday Mass, VoxAI intro, night examen, etc.), each with a `key`, local `hour`, `band`, `thresholdDays`, and a `condition` matched in code; rules outside this catalog are pruned on boot (`OnModuleInit`). Editable copy/on-off/knobs live in the DB; *when* and *to whom* (the condition **type**) is still code. **`evalCondition()`'s `switch` never falls back to "always eligible" for an unrecognized `condition` string** — an unknown value logs a warning and returns `null` (never fires). It used to fall through to the `default` branch shared with "no condition" (`null`), which meant a typo'd or mismatched `condition` (e.g. matching a rule's `key` instead of its actual condition string — `SUNDAY_MASS` is keyed `SUNDAY_MASS` but its condition is `'SUNDAY'`, not `'SUNDAY_MASS'`) silently became an unconditional daily blast to everyone instead of failing loudly. If you add a new rule, its `condition` must be one of the `case` values in `evalCondition()` or it will never fire — that's intentional, not a bug to "fix" by adding a fallback.
  - **The funnel parameters are data, not constants** (2026-09 overhaul). `NotificationSettings` is a singleton row (`id="default"`, lazy-upserted) holding `maxPerDay`/`maxNudgesPerDay`/`quietStart`/`quietEnd`/`spacingHours`/`restGapEnabled`/`urgentThreshold`; `NotificationSettingsService` reads it with a ~60s in-memory cache and **falls back to `DEFAULT_NOTIFICATION_SETTINGS` (identical to the old hardcoded values) on any DB error** — so a missing row or a DB blip behaves exactly like before. `PATCH .../settings` invalidates that cache.
  - **The "rest gap" was dead code until the overhaul** — `inRestGap` was computed and never read, so non-urgent nudges fired every day the cap allowed. It is now wired: a non-urgent rule is skipped if *any* notification went out today or yesterday (urgent rules — `priority >= urgentThreshold` — ignore it), gated by `restGapEnabled`. This is the main lever against "same handful of notifications every 1–2 days."
  - **Per-rule window thresholds are data**: `readingResume`/`rosaryLapse`/`comeback` read `rule.thresholdDays` (falling back to the old literal when `null`). `streakAtRisk`, `rosaryUnfinished`, and `voxIntro` are deliberately **not** parameterised — their windows aren't "stopped for N days" semantics. `comeback`'s 14-day upper bound stays hardcoded ("stop nagging forever", not a knob).
  - **Per-user time band** (`UserNotificationProfileService`): `classifyBand()` buckets the user's last 30 days of `UserActivity` (Brazil-local hour) into MORNING/AFTERNOON/EVENING and returns the dominant one; `< 5` events ⇒ `ANY`. `getBand()` caches the result on `UserNotificationProfile.activeBand` and recomputes lazily inside the tick when it's > 7 days stale — no dedicated cron. It **never throws** (any failure ⇒ `ANY`). The tick keeps a candidate rule only if `bandMatches(userBand, rule.band)` — `ANY` on either side (or `rule.band` null) matches, so missing data degrades to the old hour-only behavior. Relies on `@@index([UserActivity.userId, createdAt])`.
  - **Text variants** (`NotificationVariantsService`): each rule has a pool of `NotificationRuleVariant` rows (seeded 1-per-rule from the rule's own `title`/`body`/`url` on boot, idempotent). `deliver()` picks the variant this user received least recently (never-used wins, tie → lowest `order`; from the `Notification.variantId` history the tick already loads) and writes `variantId` on the new row. One variant ⇒ identical to before. The "≥1 enabled variant per rule" floor is enforced in the service (400 on disabling/removing the last one), **not** the schema.
  - **Context variables** (`NotificationContextService`): `{nome}` (user first name), `{santo}`/`{tempoLiturgico}` (from `LiturgicalCalendarService`'s 24h cache — a second instance, provided in this module). `deliver()` scans the chosen title+body for these tokens, resolves only what's present, and interpolates into both (alongside the condition's `{count}`/`{label}`). Every var has a neutral fallback (`você` / `o santo de hoje` / `este tempo litúrgico`); resolution never throws. No new network call on the hot path.
  - **`streakAtRisk()` compares `SpiritualStats.lastLoginDate`, not `lastPrayerDate`.** `prayerStreak` (and the streak count shown on the frontend Profile page) is a **login** streak — it's incremented by `ActivityService.updateLoginStreak()`, called from every `POST /activity/ping` ("entrou no app"), and has nothing to do with actually praying. `lastPrayerDate` is a *different* field, touched only by `RosaryService.finish()` / `PrayersService` when a prayer/rosary is actually completed. Comparing against `lastPrayerDate` here used to fire "you'll lose your streak" pushes on days the user had already opened the app (which is what preserves the streak) but hadn't finished a full prayer that day — a real bug users reported. If you touch this condition, keep it on `lastLoginDate`; the field name `prayerStreak` is a misnomer worth remembering, not a hint about which timestamp gates it.
  - `notifications-send.service.ts` / `push.service.ts` — fan-out: writes `Notification` rows and, for users with an active `PushSubscription`, sends a real Web Push message via VAPID (`web-push` package). A `410`/`404` response from a push endpoint means the browser subscription is dead — that subscription row is deleted immediately rather than retried.
- **`src/modules/rosary/`** — Rosary session tracking plus one "builder" file per mystery/devotion variant (`rosaryBuilder.ts`, `divineMercyBuilder.ts`, `sevenSorrowsBuilder.ts`, `stMichaelBuilder.ts`, `StJosephBuilder.ts`, `sacredHearthBuilder.ts`, `tearsMaryBuilder.ts`, `viaSacraBuilder.ts`, `HolySpiritBuilder.ts`) — each returns the static step-by-step content for that devotion; `rosary.service.ts`/`rosary.controller.ts` handle the stateful session (progress, elapsed time, history) on top. **Three independent places treat an incomplete `RosarySession` as "abandoned," each with a different window, and that's deliberate — don't collapse them into one constant:** `getSession()`/`getActiveProgress()` drop a session from "continue where you left off" after `STALE_SESSION_HOURS` (12h, since resuming a days-old session made the eventual `finishedAt - startedAt` duration meaningless); `notifications.scheduler.ts`'s `ROSARY_UNFINISHED` condition only nudges about a session between 1 and 7 days old *with real progress* (`currentStep > 0`) — any narrower and the reminder wouldn't have time to fire, any wider and it nags about a terço the UI no longer shows as resumable; `RosaryService.cleanupAbandonedSessions()` (daily cron, 03:30 America/Sao_Paulo) permanently deletes incomplete sessions after 30 days so the table doesn't accumulate orphaned rows forever — a session a user starts and never revisits for that exact `(userId, type)` pair was otherwise never touched again by any query, and used to feed false "termine seu terço" notifications indefinitely.
- **`src/modules/users/`** — account CRUD: registration (`create`, gated by `X-App` like login), profile updates, account deletion. Registration checks `password === confirmPassword` server-side (not just a frontend concern) and sends the verification email through `MailService`. **`PATCH /users/me` (`updateProfile`, name only)** is validated by `UpdateProfileDto` (`name`: trimmed, 2–80 chars) — it used to be an inline `{ name: string }` body type, which disappears at runtime and validates nothing. The service's `prisma.user.update()` call uses an explicit `select` whitelist (`id`/`name`/`email`/`pendingEmail`/`createdAt`/`emailVerified`/`isAdmin`), same pattern as `create()` — it used to spread the full `User` row minus only `password`, which leaked `emailVerificationToken`, `passwordResetToken` and `pendingEmailToken` in the response body (the verification one let a caller self-verify their account without ever opening the email). If this route ever needs to return more (e.g. `hasPassword`/`hasGoogle`), add fields to the `select`/return explicitly — never go back to a spread. **`getProfile()` (`GET /users/me`) returns `hasPassword: boolean`** — computed from `user.password != null`, the hash itself is never in the payload — so the frontend can pick "Definir senha" vs "Trocar senha" — **and `hasGoogle: boolean`** (a `LinkedAccount` with `provider = 'google'` exists), added by the `prova-identidade` spec so the frontend can tell an account that has **both** methods, **and `showWelcome: boolean`** (`user.welcomeSeenAt == null`), added by the `boas-vindas` spec — same shape as VoxAI's `showVoxIntro`; the frontend shell redirects to `/oratio/boas-vindas` while it's `true`. **The admin endpoints `GET /users/admin/users` and `GET /users/admin/users/:id` (`JwtAuthGuard` + `AdminGuard`) also return `hasPassword` + `authProviders: string[]`** (spec `admin-provedor`) — `getAllUsers`/`getUserDetail` select `password` and `linkedAccounts.provider`, map them to the booleans and **discard the raw fields**, same as `getProfile`. `GET /users/admin/users` gained a `provider` query filter (`oratio` | `google` | `both`; any other value → ignored, same tolerant parsing as `isAdmin`/`emailVerified` — never 400) that adds a `password`/`linkedAccounts` `where` clause AND-ed with the other filters: **three states, not two** — `oratio` = `password != null` + no `LinkedAccount`; `google` = `password == null` + a `google` link; `both` = `password != null` + any link (an account can have a password *and* Google). Read-only, no schema change. **`POST /users/me/welcome-seen`** (`JwtAuthGuard` only — no throttle, no `X-App`, mirrors `POST oratio/voxai/profile/intro-seen`) → `markWelcomeSeen(userId)`: stamps `User.welcomeSeenAt` with `now()` **only if still null** (`findUnique` guard), so calling it again on a completed account is a no-op — the timestamp never moves. Returns `{ ok: true }`. `User.welcomeSeenAt` is a nullable column (no migrations here — `prisma/db-scripts/2026-09-10-boas-vindas.sql` carries the `ADD COLUMN` **and** a one-time `UPDATE ... SET welcomeSeenAt = now()` backfill so the guide only shows for accounts created *after* the deploy; the `db push` for this column is its own, separate from login-google's). **`POST /users/me/set-password`** (`JwtAuthGuard` + throttle 5/min, no `X-App` — same as `change-password`) sets the **first** password for an account that never had one (Google-only): body `{ password, confirmPassword, googleCredential }`. Accepts only when `User.password` is `null` (409 → "use Trocar senha" otherwise) **and** only with a fresh Google login (2026-09-14): `googleCredential` is required by `SetPasswordDto` (missing → 400 from the ValidationPipe). Order in the service: mismatch → 400, missing user → 401, already has a password → 409 (checked *before* touching Google), then `assertFreshProof(userId, { googleCredential })` (invalid/expired id_token → 401, `sub` not linked to this user → 400), then the hash is written. Without that proof, a stolen access token on a Google-only account could create a password the attacker knows and keep access after the session dies. It **does not** revoke `RefreshSession`s (nothing was invalidated — unlike `changePassword`). `changePassword` on a passwordless account short-circuits before `bcrypt.compare(x, null)` (409 → "use Definir senha") — see §5. **`deleteAccount()` requires a fresh identity proof** before permanently deleting the user and everything cascaded from it — an access token alone (stealable via XSS, an unlocked device) used to be enough to trigger an irreversible deletion; now it isn't. It delegates to **`assertFreshProof(userId, { password?, googleCredential? })`** (spec `prova-identidade`): which proof counts comes from what the account **actually has**, not from `password == null` (the old bug — an account with a password *and* Google could never reach the Google branch). `proof.password` + the account has a password → `bcrypt.compare` (wrong → 401 `Senha incorreta`); otherwise `proof.googleCredential` → `AuthService.verifyGoogleIdentity` (the same helper as `POST /auth/google`) with the `sub` matching one of **this** user's `LinkedAccount` google rows (`sub` of another account / no link → 400; malformed `credential` → the verifier's 401 bubbles); no valid proof → 400, never 500. An account with **both** methods proves with either one — so a user who forgot their password can still exercise the LGPD right to delete. `DeleteAccountDto` (`{ password?, googleCredential? }`) is unchanged. `assertFreshProof` is `private`; its consumers are `deleteAccount` and `setPassword`, and its 400 message is generic ("Não foi possível confirmar sua identidade."). `UsersModule` imports `AuthModule` (which now exports `AuthService`) for that helper. **`setAdminStatus()`'s `ADMIN_PASSWORD` check is constant-time** (`matchesAdminPassword`, hashes both sides to SHA-256 then `crypto.timingSafeEqual`) rather than a plain `!==`, and short-circuits to `false` if `ADMIN_PASSWORD` itself isn't set — don't reintroduce a direct string comparison here, and don't let an unset env var "match" an empty candidate.
- **`src/modules/mail/`** — `MailService` posts directly to the **Brevo** transactional email HTTP API via raw `axios` (`https://api.brevo.com/v3/smtp/email`, `BREVO_API_KEY`) — not the `@getbrevo/brevo` SDK, not SMTP/`nodemailer`, not Resend (all three used to sit in `package.json` unused and were removed in 2026-09-04 — see §8). Builds Oratio-branded HTML templates inline (verification, password reset, email-change confirmation) in `buildOratioTemplate`.
- **`src/system-log/`** — `AllExceptionsFilter` (wired globally in `main.ts`) catches every exception and, for 5xx responses, appends to an **in-memory ring buffer of the last 100 entries** (`SystemLogService`). Not persisted, not a real audit log — resets on every restart/deploy. Exists purely so the admin panel can show "what broke recently" without paying for a logging service or DB writes on every error.
- **`src/prisma/`** — `PrismaService`/`PrismaModule` thinly wrap the generated Prisma client for DI; `prisma/schema.prisma` is the single source of truth for the schema (see §2 for the no-migrations caveat).

## 8. Naming, dead code, and other things that will confuse you if unexplained

- **Package name is `finance-api`, but there is no finance domain here.** The codebase is Oratio-only. Don't go looking for finance models or routes — there aren't any. Renaming the package would be a nice cleanup but touches deploy config outside this repo, so it hasn't happened.
- **This API used to also serve a second, unrelated product** ("Cravou!", a World Cup prediction pool) behind the same `X-App` header pattern. That code and its `Cravou*` Prisma models were removed once the tournament ended. `AppType` still being an enum (with one member) instead of a boolean is a remnant of that — it's cheap insurance against needing another product-routing header again, not evidence one currently exists.
- **`@google/generative-ai`, `nodemailer`, `resend`, and `@getbrevo/brevo` used to sit in `package.json` without a single import in `src/`. They were removed in 2026-09-04** (`npm uninstall`; build clean, 811 tests green). The reason they were never needed still holds and is worth knowing: VoxAI calls OpenAI **directly over HTTP** (§6), and mail goes through Brevo's **raw HTTP API**, not its SDK (§7). So if you find yourself reaching for Gemini, SMTP, Resend, or the Brevo SDK, you're adding a new dependency and a new integration path — that's an architecture decision, not a detail. Same habit applies generally: grep `src/` before assuming a package in `package.json` is actually wired up.
- **No `prisma/migrations` folder.** Schema changes go live via `npx prisma db push` directly against the database, with no recorded migration history and no automatic rollback (see §2). Be extra careful with any change that would drop or truncate data. The SQL for a pending change (with its rollback) is written to `prisma/db-scripts/AAAA-MM-DD-*.sql` for human review before anyone runs `db push` — `login-google` was the first to use this (`2026-09-08-login-google.sql`).
- **No deploy manifest lives in this repo.** If you need to know how/where this actually runs in production, ask — don't infer it from `package.json` scripts alone.
- **`POST /auth/google` responds `200`, `POST /auth/login` responds `201`.** The login is `201` only because that's Nest's default for `@Post` with no `@HttpCode` — it never created a "resource". The Google route was pinned to `200` on purpose (`@HttpCode(200)`), which better describes "session issued". Don't align them by changing login: the frontend and any client already handle its `201`. Known cosmetic inconsistency, not a bug. **`POST /users/me/legal-terms-accepted` and `POST /users/me/welcome-seen` got the same `@HttpCode(200)` fix (2026-09-14)** — both had shipped with the `@Post` default `201` even though they only mark idempotent state on an existing row, never create a resource; same reasoning as the Google route above.

## 10. Working in this codebase — conventions to follow

- **Comments explain *why*, not *what*.** This codebase already does this well in most modules (see the Prisma schema and `auth.service.ts` for examples) — keep doing it. A comment justifying a non-obvious choice (a security tradeoff, a workaround, an ordering constraint) is worth keeping; a comment restating the code below it is not.
- **`X-App: oratio`** must be sent by any client calling routes that check it (`auth`, `users`) — see `AppType` in §3/§8. This will keep existing even with one app because removing it would require the frontend and any other future client to change in lockstep.
- **Timezone-sensitive logic uses `America/Sao_Paulo` explicitly** (`date-fns-tz`, or manual `toLocaleDateString("en-CA", { timeZone: ... })`) — Oratio's user base is Brazilian, and daily resets (streaks, daily liturgy, notification `hour`) are meant to align with Brazil's clock regardless of server timezone. Don't introduce naive `new Date()` day-boundary logic in a new feature without checking how the neighboring modules handle it.
- **Guards**: `JwtAuthGuard` for anything user-specific, `AdminGuard` (stacked after `JwtAuthGuard`) for admin-only routes. Public routes (liturgy, register, login, password-reset request) intentionally have no guard — don't add one without checking whether that breaks the flow (e.g. password-reset must work for a logged-out user).
- **New Prisma models**: add a short comment on the model explaining any non-obvious constraint (why a field is unique on a compound key, why there's a `year` column, why a row is deleted vs. flagged) — this schema already sets that precedent; match it.
- Before assuming a package in `package.json` is actually used, grep for it in `src/` — see §8 for three that currently aren't.
- **Tests**: mock `PrismaService` as a plain object of `jest.fn()`s (only the methods a given test actually needs), never a real database. Mock external HTTP at the module level (`jest.mock('axios')`, `global.fetch = jest.fn()`) — nothing in this suite should make a real network call. Prefer state-based assertions (what a function returns, what a mock was called with) over asserting call sequences. See §2 for the current coverage numbers and where the convention is already followed consistently.
